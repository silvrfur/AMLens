# Database migrations

Alembic manages the `public` schema of the main PostgreSQL database. The application never creates
or alters `public` tables itself: there is no `create_all()`. The `agent_runtime` schema is
**not** under Alembic. The agents create it at runtime (see [Schema](schema.md)).

## How Alembic is configured

| File | Role |
|---|---|
| `backend/alembic.ini` | `script_location = %(here)s/alembic`, `prepend_sys_path = .`, logging. It deliberately holds **no** database URL. |
| `backend/alembic/env.py` | Imports `Base` and `database_url()` from `app.database.connection`, and registers the models from `app.database.tables`. `target_metadata = Base.metadata`, with `compare_type=True`. The URL is `config.attributes['database_url']` when tests or tooling pass one, otherwise `DATABASE_URL` from the environment or `backend/.env`, normalized to `postgresql+psycopg://`. Online migrations use a `NullPool` engine with `connect_timeout=10`. Offline (`--sql`) mode is supported. |
| `backend/alembic/versions/` | Migration scripts, with hand-written, short revision IDs |
| `backend/app/database/schema_check.py` | `assert_schema_current(engine)` runs in the backend's lifespan. If the database's current revisions differ from the scripts' heads, startup fails with `Database schema is not up to date (database: [...], code: [...]). Run \`alembic upgrade head\` from the backend/ folder.` |

Because of the startup check, a backend image can only serve a database that is at **exactly** its
own head. A database that is ahead of the code, for example after a newer migration ran, also makes
an older backend refuse to start. This matters for rollbacks (see below).

## Running migrations

All commands run from `backend/`, with the virtual environment active and `DATABASE_URL` set
(either in the environment or in `backend/.env`).

```bash
alembic upgrade head          # create or update the schema to the latest revision
alembic current               # show the revision the database is at
alembic history --verbose     # list revisions
alembic upgrade head --sql    # print the SQL instead of running it (offline mode)
```

### Downgrading

```bash
alembic downgrade -1             # step back one revision
alembic downgrade 0001_initial   # go back to a specific revision
alembic downgrade base           # drop everything (destroys all data in public)
```

`infra/seed/make-seed.sh` uses `alembic downgrade 0001_initial` followed by `alembic upgrade head`
to re-run the `0002` data backfill on rows copied from the legacy SQLite file. Never downgrade the
production database without a fresh backup. `0001` drops tables, and `0002` throws away the alert
lifecycle state.

## Creating a migration

1. Change the ORM model in `backend/app/database/tables.py`.
2. Generate a script: `alembic revision --autogenerate -m "add <thing>"`, or `alembic revision -m "..."` for a data migration. Autogenerate compares the models against a database at head, so run it against your local docker PostgreSQL.
3. Edit the generated file. Follow the existing convention of a short, readable revision ID (for example `0003_<topic>`), and set `down_revision` to the current head (`0002_alert_status`). Review every autogenerated operation, and write `downgrade()` by hand.
4. Apply it locally (`alembic upgrade head`) and run the backend tests against a throwaway database (`TEST_DATABASE_URL`). `backend/tests/test_migrations.py` checks that:
    - `upgrade` → `downgrade base` → `upgrade head` round-trips,
    - the migrated schema matches `Base.metadata` exactly (`compare_metadata` returns no diff, types included),
    - the app refuses an unmigrated database.
5. Also update anything that lists tables explicitly, if the change affects it: `backend/scripts/migrate_sqlite_to_postgres.py`, `backend/tests/conftest.py`, `deploy/aks/remove-dataset.sh`, `backend/scripts/create_readonly_role.sql` (its grants) and `infra/seed/seed.sql` (regenerate it with `make-seed.sh`).

The `models match migrations` test fails if you change `tables.py` without a migration, or the
other way round.

## Migrations in deployment

### Order of operations

In production (AKS), `deploy/aks/rollout.sh`, which the CI/CD pipeline runs, does the following:

1. Builds the `amlens-rag`, `amlens-backend` and `amlens-frontend` images, tagged with the git SHA.
2. **Migrate.** Deletes and re-creates the Job `migrate` from `deploy/aks/jobs/migrate.yaml`. The Job runs the *new* backend image with `command: ["alembic", "upgrade", "head"]` and `DATABASE_URL` from the `amlens-db` Secret. It has `backoffLimit: 2`, `ttlSecondsAfterFinished: 86400`, and the `amlens.io/db-client: "true"` label, which the network policy needs. The script waits up to 600 s for `condition=complete`. On failure it prints the last 50 log lines and **stops the rollout**.
3. Rolls out `rag`, then `backend`, then `frontend`, and waits for each.
4. Smoke-tests `https://<host>/api/backend/health` until `backend`, `agent` and `rag` are all `healthy`.

`deploy/aks/deploy.sh` (the first-time setup) uses the same migrate Job.

### The `RUN_MIGRATIONS` flag

`backend/Dockerfile` sets `RUN_MIGRATIONS=true` by default. The container command is:

```sh
if [ "$RUN_MIGRATIONS" = true ]; then alembic upgrade head; fi && exec uvicorn app.main:app --host 0.0.0.0 --port 8000
```

This is convenient for a single container started by hand. The AKS backend Deployment sets
`RUN_MIGRATIONS=false` (`deploy/aks/base/apps.yaml`), because the migrate Job runs the migrations
once, before any pod starts. With more than one replica, every pod would otherwise try to migrate
at the same time.

### Backward compatibility rule

!!! warning "Migrations run before the new backend rolls out"
    While the migrate Job runs, and during the rolling update after it, the **previous** backend
    release is still serving traffic against the **migrated** schema (see `DEPLOY.md`: "Migrations
    run before the new backend starts, so they must stay backward compatible with the previous
    release"). Every migration must therefore work with both the old and the new code:

    - **Additive first.** Add new tables, and nullable columns (or columns with a server default), in one release. Start using them in the same or a later release.
    - **Remove later.** Stop using a column or table in release *N*. Drop it in release *N+1*.
    - **Renames** follow the same pattern: add the new column, copy the data, switch the code, then drop the old column in a later release.
    - **Never** add a `NOT NULL` column without a server default, and never tighten a constraint that old code might break. Remember that the ORM defaults in `tables.py` are not server defaults.
    - Keep data migrations, like `0002`, idempotent and fast. They run inside the migrate Job's transaction.

!!! note "The startup schema check and rolling updates"
    Pods of the old release that are already running keep serving after the migration, because
    `assert_schema_current` runs only at startup. An old pod that **restarts** after the migration,
    or a rollback to an older image, will refuse to start: the database is then at a newer head
    than that image knows. To roll back the code you must first `alembic downgrade` to the old
    head, after taking a backup, or roll forward with a fix.

### Agent runtime schema changes

`agent_runtime` uses `CREATE TABLE IF NOT EXISTS`, so changing the DDL in `postgres_service.py`
does **not** change tables that already exist. To change that schema in a live environment, you
must write the `ALTER` statements yourself (for example in an Alembic migration that targets
`agent_runtime`, or a one-off script), and keep them backward compatible in the same way. Also
update `sqlite_service.py` so that local and test stores stay in step.
