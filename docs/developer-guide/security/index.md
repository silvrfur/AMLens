# Security

This page summarises what AMLens protects, the controls in place in the production AKS
deployment and in the code, and the known limitations. Production facts are labelled
**Verified live** (checked read-only against the cluster on 2026-11-25) or **From repository**.

AMLens is a demonstration deployment in a training sandbox using sample and synthetic data. The
[known limitations](#known-limitations) must be addressed before it holds real customer data.

## What needs protecting

| Asset | Where it lives | Why it matters |
|---|---|---|
| Transaction and alert data | PostgreSQL (`postgres-0`, managed disk) and nightly dumps in Blob Storage | Financial data; accounts are tokenized but amounts, dates and patterns remain |
| Investigation reports, decisions, audit trail | PostgreSQL (public schema and `agent_runtime`) | Regulatory evidence: must be complete and attributable |
| Secrets | Kubernetes Secrets in namespace `amlens` | Database password, proxy key, `TOKEN_SECRET`, AI keys, backup SAS, cookie secret |
| Analyst credentials | bcrypt hashes in Secret `amlens-htpasswd` | Access to everything above |
| AI services | Azure OpenAI and AI Search | Cost and quota abuse; the Search index holds curated guidance |

## Threat model summary

| Threat | Main controls | Residual risk |
|---|---|---|
| Anonymous internet access to data or APIs | All paths except `/api/backend/health` require sign-in at the ingress; backend and RAG have no public route | Single shared sign-in method (passwords), no MFA |
| Password guessing | Random 20-character passwords, bcrypt cost 12, `/oauth2` rate limit 20 req/min per IP | Distributed guessing from many IPs; no lockout |
| Forged user identity (impersonating another analyst in the audit trail) | Ingress overwrites `X-Auth-Request-*`; backend trusts `X-AMLens-User` only with the proxy key; signed-in name overrides body `analyst_id` | Anyone with cluster access or the proxy key can forge it. **Gap (inferred, untested):** on AKS a signed-in user can send `X-MS-CLIENT-PRINCIPAL-NAME`, which the frontend proxy reads first and the ingress does not strip; see [Frontend proxy](../modules/frontend-proxy.md) |
| Lateral movement inside the cluster | Default-deny NetworkPolicies, per-service allow rules | Egress unrestricted; no pod security standards enforced |
| Secret leakage via git or images | Secrets only in Kubernetes Secrets / git-ignored files; images built from `git archive` (no `.env`) | Keys shared outside the secret store must be rotated |
| Prompt injection or data leakage via the LLM | Agent guardrails: tool allow-list, call budget, minimal LLM payload, deterministic facts, verifier | LLM output is still free text within the allowed sentences |
| Loss or tampering of backups | Write-only SAS from the cluster; storage outside the cluster; 14-day lifecycle | No point-in-time restore; restore procedure untested |
| Compromise of the CI pipeline | OIDC federation scoped to the `production` environment; no stored cloud credentials; optional required reviewers | The pipeline identity has Contributor and full cluster access |

## Controls

### Edge and sign-in

- **HTTPS only.** Let's Encrypt certificate via cert-manager (`Certificate amlens-tls` Ready,
  verified live); cookies are `Secure`.
- **Sign-in in front of everything.** NGINX `auth-url` to oauth2-proxy on the `amlens-web`
  ingress. Verified live: `GET /` and `GET /api/backend/alerts` without a session return `302`
  to `/oauth2/sign_in`; `/api/backend/health` returns `200` with status only.
- **Rate-limited sign-in.** `limit-rpm: 20`, `limit-burst-multiplier: 2` on `/oauth2`
  (verified live).
- **Password storage.** Only bcrypt hashes in the cluster; generated passwords are shown once
  and kept in the git-ignored `deploy/aks/.credentials` until handed over.

Details and sequence diagram: [Authentication](../authentication/index.md).

### Service-to-service trust

- **Proxy key.** The backend rejects every request (except `/health` and `OPTIONS`) without the
  correct `X-AMLens-Proxy-Key`, compared with `hmac.compare_digest` (`backend/app/security.py`).
  The key is a random 32-byte value generated by `deploy.sh`.
- **Header hygiene in the frontend proxy.** Only `accept` and `content-type` are forwarded;
  cookies and tokens never reach the backend. Path segments are re-encoded to prevent path
  traversal into other upstream routes.
- **RAG service.** Has no proxy key check of its own; it relies on the network policy (only
  backend and frontend may connect) and on the ingress sign-in for `/api/rag/*`.

### Network isolation

Verified live: all Services are `ClusterIP`; only the ingress controller has a public IP. These
NetworkPolicies are in place and enforced by Cilium:

| Policy | Effect |
|---|---|
| `default-deny-ingress` | No pod accepts connections unless another policy allows it |
| `edge-from-ingress` | Frontend (3000) and oauth2-proxy (4180) only from namespace `app-routing-system` |
| `backend-from-frontend` | Backend (8000) only from the frontend |
| `rag-from-app` | RAG (8001) only from backend and frontend |
| `postgres-from-db-clients` | PostgreSQL (5432) only from pods labelled `amlens.io/db-client=true` (backend, migrate, seed, backup) |
| `acme-solver-from-ingress` | cert-manager HTTP-01 solver only from the ingress namespace |

Egress is not restricted (pods can reach the internet, including Azure OpenAI and AI Search).

### Secrets management

- **Kubernetes Secrets, created by `deploy.sh`** (verified live: `amlens-ai`, `amlens-app`,
  `amlens-backup`, `amlens-db`, `amlens-htpasswd`, `amlens-oauth`, `amlens-tls`). Values come
  from Azure (`az ... keys list`), git-ignored local files or are generated; never from
  command-line arguments and never committed.
- **Git hygiene.** `deploy/aks/.gitignore` excludes `.kubeconfig`, `.build/`, `.deploy.log`,
  `.credentials`; `.env` files are ignored throughout; `infra/seed/seed.sql` is ignored.
- **Image hygiene.** Build contexts are `git archive HEAD` exports, so git-ignored files such
  as `.env` cannot end up in an image.
- **Least privilege for search.** The RAG service gets an AI Search **query key**, which can
  only read the index, not modify or delete it (from repository: `az search query-key list` in
  `deploy.sh`; the variable is still named `AZURE_SEARCH_ADMIN_KEY`).
- **Write-only backups.** The backup SAS allows create/write only; the cluster cannot read,
  list or delete existing backups.
- Secrets are not encrypted with a customer-managed key and are readable by anyone with
  cluster-admin access (see limitations).

### Containers

From repository (Dockerfiles):

| Image | Base | Runs as |
|---|---|---|
| `amlens-backend` | `python:3.12-slim` | system user `app`, UID 1001 |
| `amlens-rag` | `python:3.12-slim` | system user `app`, UID 1001 |
| `amlens-frontend` | `node:20-alpine` (multi-stage, standalone output) | user `nextjs`, UID 1001 |
| `amlens-seed` | `postgres:16-alpine` | `postgres` |

The Kubernetes manifests set no `securityContext` (no `runAsNonRoot`, read-only root
filesystem or dropped capabilities) apart from `fsGroup: 999` on PostgreSQL; non-root execution
comes from the images' `USER` instructions. Third-party images are imported into ACR with pinned
tags (`postgres:16-alpine`, `oauth2-proxy:v7.7.1`, `curl:8.11.0`).

### Data protection in the application

- **Tokenized account identifiers.** On ingestion, bank and account numbers are replaced with
  `ACC_` + the first 24 hex characters of `HMAC-SHA256(TOKEN_SECRET, len:bank len:account)`
  (`backend/app/utils/tokenization.py`). The length prefix prevents ambiguity between
  concatenations. `TOKEN_SECRET` must be at least 32 characters; tokenization raises an
  error without it, so data is never stored untokenized.
- **Second masking layer for the agents.** `mask_account()` in `agents/services/security.py`
  hashes the account token again (`acct_` + 16 hex characters of SHA-256) before it enters the
  agent state.
- **Read-only access for the agents.** The agents read source data through `TeamBackend` in
  `READ ONLY` transactions; `AML_SOURCE_DATABASE_URL` can point them at a SELECT-only login.
- **Upload limits.** CSV uploads are limited to 20 MB in the backend
  (`MAX_UPLOAD`) and 25 MB at the ingress (`proxy-body-size`).
- **Audit trail.** Agent runs, decisions and status changes are written as audit events with the
  signed-in analyst name.

### LLM guardrails

The agents are designed so that the LLM cannot take actions or invent facts.
Source: `agents/services/security.py`, `agents/services/audit_service.py`,
`agents/agents/report_agent.py`, `agents/verifier/report_verifier.py`.

| Guardrail | Implementation |
|---|---|
| Tool allow-list | `ALLOWED_TOOLS = {"backend.read", "rag.search", "llm.generate"}`; any other tool name raises `PermissionError` |
| Call budget | `ToolBudget` allows at most 8 external calls per investigation (`ToolBudgetExceeded`); every attempt, including retries, is counted and recorded in `tool_calls` |
| No tool execution by the LLM | The LLM is called only for structured JSON (`response_format: json_object`), validated locally with Pydantic; it cannot request tools |
| Minimal payload | `safe_llm_payload()` sends only the investigation id, the list of **allowed statements** and the allowed next steps. Transaction descriptions, alert labels and retrieved passages are deliberately excluded, which also removes the main prompt-injection channel |
| Deterministic facts | Figures, evidence and citations are produced by code; the LLM only chooses narrative sentences from the approved list |
| Independent verification | `ReportVerifier` recomputes the transaction analysis, evidence and gaps, rejects any field that differs, any narrative sentence not in the approved set, changed limitations, and accusatory language (`guilty`, `criminal`, `launderer`, ...). A failed check triggers one correction attempt, then the run ends `incomplete` |
| No secrets or prompts in logs | Provider exceptions and prompt contents are not logged; settings models mark keys `repr=False` |
| Human in the loop | Reports are recommendations; only an analyst records `APPROVE`, `REJECT` or `ESCALATE`, and `APPROVE` requires a completed, verified report |

See [Agent pipeline](../modules/agent-pipeline.md) and
[Report verifier](../modules/report-verifier.md).

### Supply chain and CI

- Dependencies installed from `requirements.txt` ranges (backend, agents, RAG) and
  `pnpm install --frozen-lockfile` (frontend). `agents/requirements-lock.txt` records a tested
  set of exact versions.
- The pipeline signs in to Azure with OIDC federation (no stored secret), limited to jobs in the
  `production` environment; add required reviewers to that environment to gate releases.
- Default workflow token permission is `contents: read`.

## Known limitations

- **Analyst identity header precedence (inferred, untested).** The frontend proxy prefers `X-MS-CLIENT-PRINCIPAL-NAME` (set by Container Apps Easy Auth) over the oauth2-proxy headers, and the AKS ingress does not strip it, so a signed-in user could have a different name recorded on a decision. Fix: read only the header the active edge sets, or strip the others at the ingress.
Be explicit about these with anyone evaluating the deployment:

1. **Keys instead of managed identity.** Azure OpenAI and AI Search are accessed with API keys
   stored in Kubernetes Secrets because the sandbox does not allow the role assignments for
   workload identity. The code already supports keyless Entra ID authentication.
2. **Rotate any key that has been shared outside the secret store** (chat, e-mail, screenshots,
   tickets) — see [Rotate keys and secrets](../deployment/operations-runbook.md#rotate-keys-and-secrets).
3. **Entra ID sign-in not enabled.** Shared username/password accounts without MFA, no roles,
   no lockout, and no central offboarding; removing a user means editing a Secret.
4. **In-cluster database without point-in-time restore.** One PostgreSQL pod on one managed disk;
   recovery point is the last nightly dump (up to 24 hours of data loss), and the restore
   procedure is untested.
5. **No WAF or DDoS protection** beyond Azure's platform defaults; only `/oauth2` is
   rate-limited.
6. **Investigations run in the HTTP request** (up to the 300 s ingress timeout). Long runs tie up
   a worker and are lost if the pod restarts.
7. **Kubernetes Secrets are base64, not a vault.** Anyone with cluster-admin (including the
   pipeline identity) can read them; no Key Vault integration or customer-managed encryption.
8. **No pod security hardening** in the manifests (`runAsNonRoot`, read-only root filesystem,
   dropped capabilities) and no egress restrictions.
9. **No centralised logging or alerting** (see [Monitoring](../monitoring/index.md)): security
   events such as repeated failed sign-ins are visible only in pod logs while they last.
10. **Public endpoints for Azure services.** ACR, Azure OpenAI, AI Search and Storage are reached
    over their public endpoints.
11. **Single replicas** for every component: no high availability.
12. **Proxy key trust is all-or-nothing.** Anyone who has the proxy key and network access to the
    backend can act as any user.

The [Container Apps design](../deployment/container-apps-design.md) addresses 1, 4, 7 and 10 in
part, and lists its own remaining gaps.
