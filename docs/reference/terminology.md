# Terminology

Technical terms and exact identifiers used in the AMLens code, database, API and deployment.
Identifiers are case-sensitive and appear here exactly as in the code. For plain-language
definitions of AML and product terms (alert, typology, structuring, escalation and so on) see
the user [Glossary](../user-guide/glossary.md).

## Components

| Name | What it is |
|---|---|
| `frontend` | Next.js application (port 3000). Serves the UI and the same-origin API proxy `/api/[service]/[...path]` |
| frontend proxy | The route handler `frontend/app/api/[service]/[...path]/route.ts` that forwards `/api/backend/*` and `/api/rag/*` to the internal services, adding the proxy key and user header |
| `backend` | FastAPI service (port 8000): ingestion, alerts, investigations, decisions, audit, health. The agents run inside this process |
| agents | Python package `agents/`: the LangGraph investigation pipeline, verifier and agent runtime store |
| `rag` | FastAPI retrieval service (port 8001) over Azure AI Search (`RAG_BACKEND=azure`) or a local FAISS index (`faiss`) |
| `TeamBackend` | Adapter (`backend/app/integrations/team_backend.py`) that turns an alert into the agents' `AlertBundle`, reading in READ ONLY transactions |
| `agent_bridge` | `backend/app/services/agent_bridge.py`: builds agent services for a synchronous run from the environment |
| `TeamAzureSearchAdapter` / `TeamFAISSAdapter` | RAG search adapters for the two backends |
| `InvestigationRunner` | Runs the compiled LangGraph for one investigation (`agents/graph.py`) |
| `ReportVerifier` | Deterministic checker of the drafted report (`agents/verifier/report_verifier.py`) |
| `oauth2-proxy` | Sign-in proxy at the edge (port 4180) |
| `amlens-nginx` | Ingress class and controller of the AMLens NGINX ingress (AKS app routing) |
| `postgres` / `postgres-0` | PostgreSQL StatefulSet and its single pod |
| `postgres-backup` | Nightly backup CronJob |
| `migrate`, `seed` | Kubernetes Jobs for schema migrations and sample data load |

## Agent pipeline nodes

LangGraph node names in `agents/graph.py`, in execution order:

| Node | Class / function | Purpose |
|---|---|---|
| `transaction` | `TransactionAgent` | Loads the `AlertBundle` (via `backend.read`), masks the account, computes `transaction_analysis` |
| `retrieval` | `AMLRetrievalAgent` | Searches guidance for the alert's typology (via `rag.search`) |
| `evidence` | `EvidenceAgent` | Builds evidence claims from facts and guidance |
| `information_gap` | `InformationGapAgent` | Lists missing information and investigation questions |
| `report` | report agent | Asks the LLM (`llm.generate`) to choose narrative sentences; assembles the `InvestigationReport` |
| `verify` | `ReportVerifier` | Checks the draft against independently recomputed content |
| `correction` | report agent | One correction attempt if verification failed |
| `reverify` | `ReportVerifier` | Re-checks the corrected report |
| `persist` | function | Stores the result and final `execution_status` |

Any node that sets `execution_status = failed` routes directly to `persist`.

## Detection rule IDs

`alerts.rule_id`, produced by `backend/app/services/transaction_analysis.py` and mapped to a
typology by `RULE_TO_TYPOLOGY` in `team_backend.py`:

| Rule ID | Fires when | Typology |
|---|---|---|
| `HIGH_VALUE` | A payment of at least 1,000,000 in the configured review currency (default `US Dollar`) | `unusual_activity` |
| `REPEATED_PAIR` | At least 5 transactions between the same sender and receiver within a 48-hour burst window | `unusual_activity` |
| `RAPID_MOVEMENT_CANDIDATE` | An account receives funds and sends funds onward within 60 minutes (intermediary pattern; fund identity unverified) | `rapid_movement` |
| `FAN_IN` | Mapped for compatibility; not generated by the current detection code | `fan_in_out` |
| `FAN_OUT` | Mapped for compatibility; not generated by the current detection code | `fan_in_out` |
| `STRUCTURING_CANDIDATE` | Mapped for compatibility; not generated by the current detection code | `structuring` |

An alert with a rule ID that is not in the map is rejected by the agents adapter
(`Unsupported rule ID`). Details: [Detection rules](../developer-guide/modules/detection-rules.md).

## Typology keys

Values of `AlertContext.typology` (agents) and of the `typology` field in the search index:

| Key | Meaning |
|---|---|
| `structuring` | Splitting amounts to stay below reporting thresholds |
| `rapid_movement` | Funds passing quickly through an account |
| `fan_in_out` | Many-to-one or one-to-many flows |
| `unusual_activity` | Activity without apparent economic purpose, unusually large or repeated |

The index annotations (`RAG/scripts/update_azure_typologies.py`) also know guidance categories
that are not alert typologies: `customer_due_diligence`, `enhanced_due_diligence`,
`ongoing_monitoring`, `suspicious_transaction_reporting`, `money_mules`.

## Status values

### Alert status (`alerts.status`)

| Value | Set when |
|---|---|
| `OPEN` | Alert created by ingestion |
| `UNDER REVIEW` | An investigation is opened for the alert (note the space) |
| `DECIDED` | An analyst records a decision |

### Investigation status (`investigations.status`)

| Value | Meaning |
|---|---|
| `PENDING_AGENT` | Created, agent run not started (or returned to this state when a run could not start) |
| `RUNNING` | Agent run in progress (synchronously, inside the request) |
| `FAILED` | Agent run failed; can be run again |
| `COMPLETED` | Run finished and the report passed verification |
| `INCOMPLETE` | Run finished but the report did not pass verification after correction |
| `APPROVE`, `REJECT`, `ESCALATE` | Analyst decision recorded (the decision value becomes the status) |

`COMPLETED` / `INCOMPLETE` are the upper-cased agent `execution_status`.

### Agent `execution_status` (`agent_runtime` tables, API responses)

`completed`, `incomplete`, `failed`. A run can be started only for investigations in
`PENDING_AGENT` or `FAILED`; existing `completed`/`incomplete` results are returned instead of
re-running.

### Decisions (`DecisionIn.decision`)

`APPROVE`, `REJECT`, `ESCALATE`. `APPROVE` requires `execution_status = completed` and a passed
verification.

### Audit actions (`audit_history.action`)

| Action | Written when |
|---|---|
| `CREATED` | Investigation opened |
| `AGENT_RUN_REQUESTED` | Run started |
| `AGENT_RUN_FINISHED` | Run ended; details include `execution_status` |
| `AGENT_RUN_FAILED` | Run raised an error |
| `DECISION_RECORDED` | Decision saved; details include `decision` and `analyst_id` |

### Report enums (agents schemas)

| Type | Values |
|---|---|
| `GapStatus` | `confirmed_missing`, `not_provided`, `not_applicable`, `available_verified` |
| Evidence `claim_type` | `observed_fact`, `supported_interpretation`, `unsupported_assumption`, `potential_concern` |
| Evidence `support_status` | `supported`, `limited`, `unsupported` |
| `transaction_type` | `deposit`, `withdrawal` |

### Health values (`GET /health`)

`healthy`, `degraded` (running on a local mock), `offline`, `not_applicable` (component not part
of this deployment, e.g. `queue`).

## Identifiers and tokens

| Identifier | Format | Notes |
|---|---|---|
| Dataset id | 20 hex characters | First 20 characters of the SHA-256 of the uploaded CSV file |
| Account token | `ACC_` + 24 hex | HMAC-SHA256 of bank and account with `TOKEN_SECRET` (`sender_token`, `receiver_token`, `anchor_account_token`) |
| Agent account mask | `acct_` + 16 hex | SHA-256 of the account token, used inside the agent pipeline |
| Investigation, decision, report version, audit ids | UUID strings (36 characters) | |
| `chunk_id` | e.g. `RBI_KYC_Master_Direction_p23_structuring_1` | Stable id of a guidance chunk; used as citation reference |
| Image tag | Commit SHA (full from CI, short from scripts) | `amlens-<app>:<tag>` in ACR |

## Agent guardrail terms

| Term | Meaning |
|---|---|
| `ALLOWED_TOOLS` | `backend.read`, `rag.search`, `llm.generate`: the only external calls an investigation may make |
| `ToolBudget` | Per-investigation counter, limit 8 external calls; `ToolBudgetExceeded` when exhausted |
| `safe_llm_payload` | The minimal data sent to the LLM (investigation id, allowed statements, allowed next steps) |
| approved statements | Evidence-grounded sentences generated by code; the only sentences the LLM may pick |
| `LLMUnavailable` | Raised when the LLM provider fails after retries or with a non-retryable error |

## HTTP headers

| Header | Set by | Read by |
|---|---|---|
| `X-Auth-Request-User`, `X-Auth-Request-Email` | oauth2-proxy, copied onto the request by NGINX | Frontend proxy |
| `X-MS-CLIENT-PRINCIPAL-NAME` | Container Apps Easy Auth (design only) | Frontend proxy |
| `X-AMLens-Proxy-Key` | Frontend proxy (`AMLENS_PROXY_KEY`) | Backend `require_proxy` (`AML_PROXY_KEY`) |
| `X-AMLens-User` | Frontend proxy | Backend, as `request.state.user` |
